# 创意动画制作需求（animation-brief）

把用户的一句创意，写成两份能直接交给制作方的文件：《X剧本》和《X_制作需求》。需要时再渲染 3 张效果图。全程用中文和用户沟通。

## 0. 先读规则文件

- 类目与标签：优先读仓库里的 `.kiro/steering/animation-taxonomy.md`；没有时读本 skill 的 `references/animation-taxonomy.md`。只能用里面已有的类目路径和标签名，不能自创。
- 出题指南：`references/test-point-guide.md` 写了 19 个考点各自的考察核心、示例，以及强耦合规则和档位配方。设计剧本的动作之前先读它。
- 考点与分级：优先读仓库里的 `.kiro/steering/animation-test-points.md`；没有时读本 skill 的 `references/test-points.md`。考点名称和分级只能用表里已有的。
- 输出规格：仓库里有 `.kiro/steering/animation-output-spec.md` 时以它为准；没有时默认 1280×720、30 帧/秒。

## 1. 理解创意

- **创意还很模糊**（例如"想做个炫酷的植物生长动画"）：先给 3–5 个方向，用表格列出 `方向｜分类路径｜画面（8–12 秒）｜炫在哪｜制作难度`，让用户选。不要直接开写。
- **创意已经具体**（有主体、有动作）：直接按默认方案写。写完后，在回复末尾列出"我自己定的默认设定"，请用户确认或修改。
- 只在会明显改变结果的问题上提问，比如结尾停在哪、风格写实还是卡通、单独成片还是并入别的任务。每个问题都给一个默认答案，让用户可以只回一句"按默认"。
- 用户同时提出几个任务时，先说清楚先做哪个，其余的排队。

## 2. 先定题目档位

- 动作设计要围绕考点来做：先按用户的要求或题材定档位（基准档、进阶档、上限档），再按 `references/test-points.md` 的配方选出 1 组强耦合的考点，最后让剧本里的关键动作正好落在这些考点上。
- 用户没指定档位时，按题材选最自然的一档，并在回复里说明；用户要"更难""更惊艳"时往上限档靠。
- 所有考点必须作用在同一个核心运动主体上，或在同一条接触、抓取、因果链上。不能为凑考点在画面里摆互不相干的主体。
- 方向推荐表里也要写出每个方向能达到的档位和考点组合。

## 3. 硬性规则（每个任务都适用）

| 项目 | 规则 |
|---|---|
| 时长 | 8–12 秒，默认约 12 秒；Prompt 写成"约 12 秒（允许 11–13 秒，不得少于 8 秒）"。内容实在放不下时最长约 15.6 秒，但必须先征得用户同意 |
| 运动 | 主体自身必须有真实可见的运动或形变，不能只靠镜头运动 |
| 声音 | 无声音 |
| 规格 | 16:9，1280×720，30 帧/秒（以 output-spec 为准）。剧本「基本设定」、Prompt「输出规格」和验收表三处写成完全相同的数值 |
| 软件 | Prompt 第一句以"使用 Blender 5.0.0"开头 |
| 内容 | 默认不出现人物、可读文字和真实品牌；造型原创，不照搬现有电影、游戏或真实产品 |
| 提示词用语 | 描述画面、运动、节奏和镜头；可以用专业动画术语（关键帧、缓入缓出、IK 约束、刚体/布料模拟、形态键、景深变焦等）；严禁出现"写脚本/写代码"、代码指令、API 函数名、属性变量名或编程步骤 |
| 镜头 | 默认一镜到底。分类规则允许剪辑，但用了剪辑就要在剧本里写清每个镜头 |

## 4. 输出格式：单文件

- 每个任务只输出一个文件：`<任务文件夹>/<标题>.md`，UTF-8 带 BOM（Python 用 `encoding='utf-8-sig'` 读写）。Prompt 和剧本合在同一个文件里，不再单独输出剧本文件和"制作需求"文档。
- 结构严格按 `references/single-file-template.md`：
  1. **考题目（Prompt、剧本）**：开头一段"基于《X剧本》，用 Blender 5.0.0 制作……"，写明时长、风格、规格；然后"核心考点如下："按编号逐条写每个考点在片中怎么体现，每条标出"（考点 N，L?）"；然后一段"另外，……"写禁止项和可调整范围；最后"以下是《X剧本》："接上剧本正文。
  2. **剧本正文**：用连贯段落写。先一段基本设定（时长、帧率、总帧数、分辨率、一镜到底、无声音），再写场景布局、材质细节，然后按"第 X–Y 秒（段落名）"逐段写动作和镜头，最后一段写灯光与成像要求。
  3. **考点**：题目档位（含配方）、耦合链、考点表、最高分级。
- 类目路径照常按分类表选定，但**不写进文件**，只在回复用户时说明类目和归类理由。
- 文件名和标题都不带版本号（不要 v2、_新版 之类）。

## 5. 写作要求

- 所有尺寸、距离、速度、时间都写成具体数字，并说明是参考值。
- 动作按秒写清"谁在什么时候做什么"，第一帧就要在动，结尾停在主体仍在运动的时刻。
- 写实类任务按 `references/realism-checklist.md` 写进具体的材质和结构细节。用户说"更写实一些"时，按清单加细节。
- 检查物理和镜头逻辑，例如镜头要停到某物的后上方，那么它必须先从镜头下方经过。
- "核心考点如下"里的描述和剧本正文的对应段落要说同一件事，数字一致。
- 只写画面、运动、节奏和镜头；可以用专业动画术语，不能出现写脚本、写代码、代码指令、API 名或属性名。

## 6. 旧格式（仅用于修改旧任务）

2026-11-19 以前的任务是"剧本 + 制作需求"两个文件，模板见 `references/script-template.md` 和 `references/brief-template.md`。修改这些旧任务时保持原格式，除非用户要求转换成单文件。

## 7. 校验（每次修改后都要跑）

用本 skill 目录下的 `scripts/check_brief.py`（在仓库里是 `.kiro/skills/animation-brief/scripts/check_brief.py`）：

```bash
python3 <skill 目录>/scripts/check_brief.py <任务文件夹>/<标题>.md
```

脚本按文件名自动选择格式。单文件（`<标题>.md`）检查：BOM、开头句式、时长、分辨率/帧率/总帧数是否一致、"核心考点如下"是否覆盖考点表里的每个考点、"第 X–Y 秒"分段、代码类用语、考点名称和分级、档位配方、耦合链、最高分级；文件里如果仍写了类目，也会核对路径。旧格式（`<标题>_制作需求.md`）按原来的规则检查。有 ERROR 必须修好；WARN 要逐条确认。

## 8. 提交

- 遵守仓库的分支规则：当前分支不是 main/master 时直接提交到当前分支；是默认分支时新建分支。
- `git add` 只加明确的文件路径；提交后 `git push`，再用 `gh api "repos/<owner>/<repo>/git/trees/<branch>?recursive=1" --jq '.tree[].path'` 确认文件已经在远端。
- 回复里给出 GitHub 链接：`https://github.com/<owner>/<repo>/blob/<branch>/<路径>`。

## 9. 效果图（只在用户要求时做）

- 用户说"不用生成图片，只改剧本和 prompt"时，不要渲染。
- 默认按剧本里的 3 个关键时刻各出 1 张，分辨率 1280×720，放在 `<任务文件夹>/效果图/`，文件名形如 `01_种子破土.png`。
- 做法、命令和踩过的坑见 `references/mockup-guide.md`；下载 Poly Haven 素材用 `scripts/fetch_polyhaven.py`。
- 先用低分辨率、低采样做测试图，亲眼看过、确认没有明显问题后，再渲染终稿。
- 交付时如实说明效果图和剧本的差距，例如程序化建模的细节不足、静帧看不出运动，并说明素材的授权（Poly Haven 是 CC0）。

## 10. 回复用户的格式

完成后用中文简短回复，依次包含：

1. 文件链接（一个文件）。
2. 一张时间线表（时间｜段落｜画面）。
3. 类目（完整路径）和一句归类理由。
4. **考点与指南说明**：用表格列出选中的每个考点：编号、名称、分级、出题指南里该考点的考察核心（用一句话概括 `references/test-point-guide.md` 的原意），以及它在本片中的具体体现。
5. **考察点与难度情况**：
   - 题目档位，以及它对应出题指南"档位配方"里的哪一条组合；
   - 耦合链：这些考点如何作用在同一主体上，或串成同一条接触、因果链；
   - 难度来源：本片最难做对的地方在哪、最容易穿帮的点是什么；
   - 片中有、但因配方或强耦合规则没有列为考点的效果，以及如果要升档或降档可以怎么调整。
6. "我自己定的默认设定"（编号列出），以及仍在等用户回答的问题。

不写开场白和结尾客套话，不复述用户已经知道的内容。
